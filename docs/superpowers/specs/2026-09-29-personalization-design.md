# Personalization (Corrections + Per-User Retraining) — Design

Status: draft, pending review
Date: 2026-09-29
Scope: `app/backend/` (new personalization routes, retrain pipeline, one
migration), `app/frontend/` (correction UI, personalized model loading), and
one new offline script under `scripts/`. The base models and
`scripts/export_onnx.py` are reused, not changed.

Supersedes the personalization parts of
`2026-08-10-smart-email-app-design.md` (§5.3's "Personalization" bullet,
§5.4's feedback-logging/custom-category bullets, §6's server schema, the
retrain-trigger item in §10, and the reversibility claim in §7). See §9 below
for exactly what changed and why.

## 1. Goal

Proposal Objective 7: client-side classification by default, with an
*optional* server-side path that retrains the models on a user's own
corrections. A user fixes a wrong label (or invents a custom category), and
future emails like it come out the way they labeled them.

Success is measurable, not just "it adapts": see §8 for the before/after
protocol used in the report.

## 2. Decisions

| Question | Decision |
|---|---|
| Mechanism | **One retrain pipeline for all corrections**, including custom labels. No separate nearest-neighbor path. |
| What gets refit | **Only the classifier head.** TF-IDF vocabulary, idf, scaler, and one-hot order stay fixed. |
| Custom labels | **Category only.** Priority buckets (low/medium/high) and spam/ham are fixed sets. |
| Trigger | **Automatic after 5 new corrections**, plus a manual "retrain now" button. |
| Promotion | **Validation gate** must pass before a new version goes active; otherwise the previous version stays. |
| Consent | **Opt-in**, per user. Opting out deletes that user's corrections and personalized models. |
| Priority | Classifier **and** regressor both retrain; a corrected bucket maps to a representative score. |

Custom labels start weak: a classifier can't generalize a new class from one
or two examples, so a fresh custom category gets better as the user labels
more emails into it. Accepted as a documented limitation rather than adding
a second mechanism to cover the cold start.

## 3. Why fixed vocabulary makes this cheap

All four exported ONNX graphs are already headless (`scripts/export_onnx.py`):
each contains only the final fitted classifier/regressor on a dense float
vector. Everything that turns an email into that vector lives outside the
graph, in `*.vocab.json` plus the TypeScript port (`tfidf.ts`, `features.ts`),
which is verified bit-exact against sklearn.

So a retrain that keeps the vocabulary fixed:
- produces vectors in exactly the same space the client already builds,
- needs no change to `tfidf.ts` or re-verification of bit-exactness,
- exports with the same `convert_sklearn(clf, ...)` call `export_onnx.py`
  already uses.

The fit itself is small: the base sets are roughly 1,000 to 1,500 rows, and
the production hyperparameters are reused via `sklearn.base.clone()`, so no
grid search runs at retrain time. Expected cost is seconds, with the
RandomForest priority classifier the slowest; measure it during
implementation.

## 4. Retrain pipeline

### 4.1 Offline precompute (once, not per retrain)

New script `scripts/export_training_matrices.py`. For each of spam, category,
and priority, it reuses that model's own trainer data-assembly code (same
source files, same seeds, same samples) and passes the rows through the
production pipeline's **already fitted** feature transformer. Output, per
model, saved as sparse `.npz`:

- `X_base`, `y_base`: the exact rows the production model was fit on.
  (Priority also gets `y_base_score` for the regressor.)
- Gate evaluation set:
  - category and priority: the 100-email adversarial set
    (`scripts/priority/adversarial_test_set.py`) vectorized the same way,
    with ground-truth labels. Priority's category one-hot and `spam_conf`
    inputs use the base category and spam models' predictions.
  - spam: a held-out slice of its base data (spam has no adversarial set).

Output goes to `app/backend/training_data/`, gitignored and regenerated by
the script, the same convention the ONNX exports already follow.

### 4.2 Retrain job

Runs as a FastAPI background task (in the threadpool, so it doesn't block the
event loop). One job at a time per (user, model); a second trigger while one
is running is skipped.

1. Load `X_base`, `y_base`, and all of this user's corrections for this model
   (across all of the user's email connections).
2. Stack them. Corrections get `sample_weight = CORRECTION_WEIGHT` (start at
   10, tune using §8); base rows get weight 1. Without weighting, 5
   corrections against about 1,500 base rows would barely move the model.
3. `clone()` the production estimator and fit.
   - Priority: fit both classifier and regressor. A corrected bucket maps to
     a regressor target of low 0.2, medium 0.5, high 0.8.
4. Run the validation gate (§4.3).
5. Export to ONNX. Store a `personalized_models` row with the metrics, status
   `active` or `rejected`. If active, the previous active version for that
   (user, model) becomes `superseded`. For priority, classifier and regressor
   are promoted or rejected together.

### 4.3 Validation gate

A new version goes active only if all of these hold:

- **Took effect:** it predicts at least 80% of the user's own corrections as
  corrected. This is a sanity check that the retrain changed anything, not an
  accuracy estimate (it's measured on training rows).
- **Didn't break general behavior:** accuracy on the gate evaluation set
  (§4.1) drops by at most 3 points versus the base model.
- **Custom labels (category):** gate-set emails predicted as a custom label
  are left out of the accuracy calculation, since the gate set's ground truth
  only knows Work/Personal/Other. If more than 10% of gate-set emails get
  predicted as custom labels, the model is overshooting and is rejected.

Thresholds (80%, 3 points, 10%) are starting values and live as named
constants.

## 5. Data model changes (one Alembic migration)

- `users.personalization_enabled` — boolean, default false.
- `corrections.provider_message_id` — string, not null. Unique on
  (`email_connection_id`, `provider_message_id`, `model`); re-correcting the
  same email for the same model replaces the earlier row.
- `corrections.feature_vector` — stays JSONB, but holds a **sparse** vector
  `{"dim": int, "indices": [int], "values": [float]}`. Dense vectors run to
  thousands of dimensions, nearly all zero.
- New table `personalized_models`:

| column | type | notes |
|---|---|---|
| id | uuid PK | |
| user_id | uuid FK → users.id | |
| model | enum: spam, category, priority, priority_regressor | |
| version | int | per (user, model), increments |
| status | enum: active, rejected, superseded | |
| onnx | bytea | the exported graph |
| classes | JSONB | output class order, including any custom labels |
| correction_count | int | corrections used in this fit |
| metrics | JSONB | gate results: own-correction accuracy, gate-set accuracy vs base, custom-label fraction, error message if the job failed |
| created_at | timestamptz | |

Models are per user, not per email connection: classification is about the
person, and a user's Gmail and Outlook corrections both feed the same model.

No `custom_categories` table. A custom label exists once some correction
uses it; the list is the user's distinct `corrected_label` values outside
Work/Personal/Other.

## 6. API

All routes use the existing `get_current_session` dependency. Correction and
retrain routes return 403 when `personalization_enabled` is false.

| Route | Purpose |
|---|---|
| `PUT /personalization/settings` | Opt in or out. Opting out deletes the user's corrections and personalized models. |
| `POST /personalization/corrections` | Upsert one correction: model, provider_message_id, sparse feature_vector, predicted_label, predicted_confidence, corrected_label. Schedules a retrain for that model once 5 corrections have accumulated since its last attempt. |
| `POST /personalization/retrain` | Manual trigger for all models that have new corrections. |
| `GET /personalization/status` | Enabled flag; per model: correction count, corrections until next auto retrain, whether a job is running, last attempt's status and metrics; the user's custom labels. |
| `GET /personalization/models` | Manifest of the user's active models: model, version, classes. |
| `GET /personalization/models/{model}/{version}.onnx` | The graph bytes. Versioned path, so the browser can cache it safely. |

## 7. Frontend

- **Correction picker** in `email-detail.tsx`: clicking the category strip,
  priority gauge, or spam badge opens a picker. Category offers
  Work/Personal/Other, existing custom labels, and "new label…". The
  corrected label shows on that email immediately, before any retrain.
- **First-time opt-in prompt** when the user tries their first correction,
  explaining what gets sent (see §10).
- **Feature vector at correction time:** rebuilt from the email still in
  memory with the existing `build*Vector` functions (priority uses the
  category label, spam confidence, and sentiment from the stored result),
  then encoded sparse.
- **Sidebar:** a line like "3 corrections · retrain at 5 · retrain now", the
  last retrain result, and custom labels in the category nav alongside
  Work/Personal/Other.
- **Model loading (`engine.ts`):** after connecting, fetch the manifest and
  load personalized graphs in place of base ones where present, using the
  manifest's `classes` for label mapping. After a retrain becomes active,
  reload those sessions. Session creation stays sequential (the existing
  onnxruntime-web single-flight constraint) and must not overlap an
  in-progress classify loop.

## 8. Measuring the result (for the report)

1. Correct N emails from a real inbox.
2. Retrain on half; hold out the other half.
3. Report accuracy on the held-out half before and after, plus gate-set
   accuracy before and after to show nothing else regressed.
4. Repeat for a few `CORRECTION_WEIGHT` values to justify the chosen one.

## 9. Changes from the 2026-08-10 design

- **Mechanism:** the old plan used centroid/kNN for low-volume custom
  categories and promoted to retraining past a threshold. Replaced with one
  retrain pipeline to keep a single code path; the cold-start weakness for
  new custom labels is accepted and documented instead.
- **Schema:** `model_versions` (with a `strategy` column and JSONB artifact)
  becomes `personalized_models` (ONNX bytes, gate metrics, status). The
  `custom_categories` table is dropped as unnecessary.
- **Client storage:** the IndexedDB correction queue with a `synced` flag is
  not built. Corrections go straight to the backend, only when opted in; a
  failed submit is shown to the user rather than queued.
- **Retrain trigger** (old §10 open question): resolved as auto-after-5 plus a
  manual button.
- **Privacy claim:** the old §7 said feature vectors can't practically be
  turned back into text. That understates it; see §10.

## 10. Privacy

Raw subject and body still never leave the browser. What does leave, only
after opt-in, is a sparse TF-IDF vector plus header/style numbers. Combined
with the public `vocab.json`, that vector reveals **which vocabulary words
appeared and their weights** (a bag of words), though not word order or any
word outside the fixed vocabulary. It isn't raw text, but it isn't anonymous
either. So:

- personalization is opt-in, and the opt-in prompt says this plainly;
- corrections are stored per user and never pooled into a shared model;
- opting out deletes them;
- the report states this limitation instead of claiming the vectors are
  irreversible.

## 11. Error handling

- **Retrain job raises:** recorded as a `rejected` attempt with the error in
  `metrics`; the active version is unchanged.
- **Gate rejects:** same, with the failing check in `metrics`; the sidebar
  shows why.
- **Personalized model fails to load in the browser:** fall back to the base
  model for that model type and show a small warning.
- **Correction submit fails:** inline error; the on-screen override is
  reverted.
- **Backend unreachable:** base models keep working. Personalization is
  strictly additive.

## 12. Testing

- **Backend (pytest):** weighted corrections flip predictions on a small
  synthetic base set; the gate rejects an overshooting model and a no-effect
  model; re-correcting the same email replaces the row; opt-out deletes data;
  routes return 403 when not opted in.
- **Frontend (vitest):** sparse encoding round-trips; a parity fixture shows
  the sparse vector from the TypeScript port matches sklearn's transform for
  the same email (same approach as the existing TF-IDF fixture test).
- **End to end (headless browser, existing Playwright convention):** opt in,
  correct 5 emails, wait for the retrain, reload, confirm similar emails
  flipped.

## 13. For implementation planning to verify

- Exactly which rows each production model was fit on (for example, whether
  spam was refit on all rows after its held-out evaluation), so `X_base`
  matches.
- Actual retrain time for the RandomForest priority classifier.
- The starting `CORRECTION_WEIGHT` value (§8 decides the final one).
